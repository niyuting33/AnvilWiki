# 页面验收与存档规范

本目录保存 Emberville Wiki 每个首页、栏目页、工具页、文章页和法律页的验收记录。页面只有通过下面三关，才可以标记为“已验收”并进入正式构建。

## 第一关：机器检查

每次验收至少运行：

```bash
pnpm check-content && pnpm build && pnpm check-links
```

- 三条命令必须以退出码 0 完成，最后不得出现红色 error。
- 任一命令失败，先修复根因，再从失败命令开始重跑；最终存档只记录最新一次完整通过结果。
- 涉及功能或共享组件时，还要运行对应的 Vitest 文件，并在记录中写明测试文件、测试数量和结果。
- `pnpm check-links` 必须在最新一次 `pnpm build` 之后执行。

## 第二关：浏览器验收

用 `pnpm dev` 打开页面，至少检查桌面宽度和手机宽度：

- 标题、首屏直答、正文、表格、按钮、导航、图片和视频均可见且清晰。
- 正文与背景对比度足够，不存在看不清的深色字；页面没有意外横向溢出。
- 宽表格在手机端可横向滚动，不把整个页面撑宽。
- 代码块或兑换码的复制按钮可用；图片、视频和外链可以打开。
- 不保留空入口、空交互控件、死链、占位文案或只显示标题的薄内容页面。
- 页面涉及共享组件时，在验收记录中单列“共享组件影响面”，至少抽查每一种受影响页面。

## 第三关：事实与发布状态

- 只发布有来源支持的信息；不确定的数值、名称、配方、兑换码等写为 `[待补充]`，不得猜测。
- 核心信息未核实、整篇仍依赖未验证素材时，保留 `draft: true`。
- `draft: true` 页面只允许开发环境查看，不得在正式构建、导航、站点地图或验收通过清单中当作已发布页面。
- 验收记录必须列出 `[待补充]` 清单；没有时明确写“无”。
- 已发布内容出现版本敏感信息时，记录 `gameVersion` 或来源时间，并在更新后重新验收。

## 一页一个存档点

- 从 [`page-acceptance-template.md`](./page-acceptance-template.md) 复制一份记录，文件名建议为 `YYYY-MM-DD-<route-slug>.md`。
- 单页通过三关后，提交该页面源码、必要的测试和对应验收记录；提交信息建议为 `content(<slug>): accept <page title>`。
- 影响多个页面的导航、页脚、主题、布局或共享组件，使用独立记录与独立提交，例如 `fix(ui): improve article contrast`。
- 一次提交只对应一个可说明的验收点。若页面后来改坏，可准确回到上一份通过状态。
- 当前站点第一次纳入本制度时，允许建立一次“上线基线”提交；之后恢复一页一提交。

## 禁止进入存档提交的文件

以下内容即使出现在工作区，也不得随页面验收提交：

- `dist/`、`.astro/`、Pagefind 输出、缓存和其他可重新生成的构建产物。
- `.env*`（`.env.example` 除外）、访问令牌、私钥、账号凭据和本地配置。
- 临时截图、浏览器下载、调试日志、一次性脚本输出。
- `*-backup*`、`*-before-*` 等本地备份素材，除非用户明确决定把它作为正式站点资产。
- 与本页无关的用户改动。

提交前必须运行 `git diff --cached --name-only` 与 `git diff --cached --stat`，确认暂存区只包含耐久源码、内容、测试和验收文档。
