# Emberville 页面验收与存档设计

## 目标

把“每写完一篇、验收一篇”变成仓库内可追踪的强制流程。首页、分类页、工具页和文章内页必须留下机器检查、桌面与手机视觉检查、功能检查、待补充项及 Git 存档点，避免仅凭口头确认上线。

## 当前约束

- 工作区已有一次完整 Emberville 改造但尚未形成 Git 基线，不能假装这些历史改动天然属于某一篇文章。
- `dist/`、缓存、日志、环境变量、临时截图和本地备份不进入 Git。
- 公共组件会同时影响多页，必须作为“全站组件”存档，不强行归入单篇文章。
- 未核实的游戏信息继续使用 `[待补充]`；若它影响页面核心结论，则页面保持 `draft: true`。

## 方案

采用“当前站点基线 + 后续一页一存档”的方式：

1. 当前已完成改造作为一个上线前基线提交，提交前完成全站机器门禁和页面清单验收。
2. 新增统一验收规范、页面级验收模板和本次基线验收报告。
3. 后续每篇页面在报告中占一条记录；内容页验收后独立提交。
4. 共享导航、主题、SEO、布局等改动使用独立的全站组件提交。

未采用的方案：把现有工作区倒拆成数十个历史提交，风险高且容易错误拆分共享依赖；只留文档不提交 Git，无法提供可靠恢复点。

## 三关流水线

### 第一关：机器检查

- 必跑 `pnpm check-content && pnpm build`。
- 构建后必跑 `pnpm check-links`。
- 与页面相关的聚焦测试必须通过。
- 失败必须修复后重跑；不得只报告失败。

### 第二关：页面检查

- 桌面端：标题、正文层级、颜色对比、图片、视频、表格、按钮和导航。
- 手机端：无横向溢出，表格可横滑，按钮可点击，标题不截断，媒体尺寸正常。
- 功能：复制、折叠、搜索、语言切换、视频 fallback 等按页面实际功能检查。
- 页面不得出现空入口、模板占位语、404 链接或无法使用的控件。

### 第三关：事实与发布检查

- 只发布已核实信息；冲突以官方来源为准。
- `[待补充]` 必须进入验收报告。
- 核心信息不足时保留 `draft: true`，不进入正式构建。
- 验收报告记录检查日期、页面 URL、结论和对应 commit。

## Git 存档规则

- 本次创建一个 `chore: archive Emberville launch baseline` 基线提交。
- 此后内容页使用 `content: add <page>` 或 `content: update <page>`。
- 全站组件使用 `feat:` / `fix:` 独立提交。
- 永远不提交 `dist/`、`.astro/`、`node_modules/`、环境文件、临时报告和本地备份。
- 提交前先查看 staged diff，确保没有密钥、缓存或意外文件。

## 验收结果

仓库中将保留：

- 一份长期维护的验收规范；
- 一份可复制的单页验收模板；
- 一份 2026-10-31 上线前基线报告；
- 一个可恢复的 Git 基线提交。
